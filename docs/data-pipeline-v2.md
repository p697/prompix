# 数据管线 v2：模型插件、控制面与指挥官

2026-11-06。本文是新管线的总体设计。第一部分（模型插件层和控制面）已在本 PR 实现并测试；第二部分（常驻后台进程）是下一步，接口已按本文预留。

## 目标

- 调用哪家模型、走订阅还是按量 API，只是配置；新增一家只加一个适配器。
- 你对任何一个 agent（Codex、Claude Code 或之后的其他工具）说一句话，它就能查看、启动、暂停管线，或者换模型；换了哪个 agent 都能接着管。
- 后台管线自己跑，不依赖某个对话窗口开着；出问题主动报警，指挥官不用每分钟去看。
- 能快则快、能省则省；质量和安全一条都不让。

## 三层结构

```
你 ──说话──▶ 指挥官（任意一个 Codex / Claude Code 会话）
                 │  只通过 npm run pipeline -- … 读写
                 ▼
            控制面（~/.local/share/prompix/pipeline/）
            config.json 期望状态 · status.json 实际状态 · events.jsonl 记录
                 ▲  读配置、写心跳和记录
                 │
            后台管线（常驻进程，下一步实现）
            采集 → 预筛 → 合并审核 → 安全复核 → 发布 → 翻译
                 │  每个环节按路由调用
                 ▼
            模型插件层（ingest/models/）
            codex-cli · claude-cli · kimi-code · kimi-api · deepseek-api · openai-api · anthropic-api
```

指挥官不直接调用模型做审核，也不直接改控制目录里的文件；它只发命令和看状态。后台进程只读配置，不接受对话里的指令。两边通过控制面解耦，所以任何一个 agent 都能接手。

## 模型插件层（已实现）

每个提供方实现同一个接口：给它可信的说明、不可信的原始内容、一份 JSON Schema（可选图片），它返回一个符合 Schema 的对象。环节代码只认这个接口。

| 提供方 | 方式 | 默认模型 | 看图 | 结构化输出 | 需要 |
|---|---|---|---|---|---|
| `codex-cli` | Codex 本地订阅，`codex exec` | gpt-5.6-luna | 是 | 原生 Schema | 本机已登录 Codex |
| `claude-cli` | Claude Code 本地订阅，`claude -p` | claude-opus-5-5 | 是 | 原生 Schema | 本机已登录 Claude Code |
| `kimi-code` | Kimi 会员订阅，`api.kimi.com/coding/v1` | k3.1-pro | 是 | JSON 模式 + 提示里的 Schema | `KIMI_CODE_API_KEY` |
| `kimi-api` | Kimi 开放平台按量 | 需在路由里指定 | 是 | 同上 | `MOONSHOT_API_KEY` |
| `deepseek-api` | DeepSeek 官方按量 | deepseek-chat | 否 | 同上 | `DEEPSEEK_API_KEY` |
| `openai-api` | OpenAI Responses 接口 | gpt-6.1-sol | 是 | 严格 Schema | `OPENAI_API_KEY` |
| `anthropic-api` | Anthropic 官方 SDK | claude-opus-5-5 | 是 | 原生 Schema | `ANTHROPIC_API_KEY` |

安全约束在插件层统一落实，任何环节都绕不开：

- 原始内容只放在 `<untrusted_source_data>` 块里，块本身不能被内容提前关闭；说明只放在系统提示里。
- 命令行订阅一律关掉工具：Codex 只读沙箱、无 shell、无联网；Claude Code `--tools ""`、不加载 MCP 和技能、不保存会话。原始内容走标准输入，不进命令行参数。
- 所有返回都再用该环节自己的 zod Schema 校验一遍，不合格即失败，不会「差不多就用」。
- 拒答（`refused`）不自动换模型重试：这条内容直接判为不发布，并记下原因。
- 错误统一成几类：`rate_limited`、`timeout`、`failed` 可以稍后重试；`unavailable`（未登录、无额度、无此模型）、`refused`、`invalid_output`、`unsupported` 需要换路由或交给人。
- 记录里只有环节、提供方、模型、耗时、token 和结果，从不写入提示词或模型输出。

密钥放在 `~/.config/prompix/models.env`（权限 600）。命令只报告缺哪个变量名，从不打印值；文件权限过宽会提示。

新增一家提供方：在 `ingest/models/registry.ts` 加一条定义，写一个实现 `ModelProvider` 的适配器，在 `ingest/model-providers.test.ts` 补测试。环节代码和控制面都不用改。

## 控制面（已实现）

目录：`~/.local/share/prompix/pipeline/`（可用 `PROMPIX_PIPELINE_DIR` 改）。

- `config.json`：期望状态（运行／暂停／停止）、每天目标、每个环节用哪个提供方和模型。每次修改都经过完整校验，多个 agent 同时修改会排队，不会互相覆盖。
- `status.json`：后台进程每分钟写一次心跳、当前环节、今天的数量和最近错误。超过 5 分钟没心跳就视为已退出。
- `events.jsonl`：只追加的记录。谁在什么时候改了什么、为什么；每次模型调用的摘要；备注。

`status` 也会报告旧的定时任务（launchd `dev.prompix.collect`）是否启用、上次运行记录是否已过期、锁的持有进程是否还在，避免任何 agent 把一份过期的「running」当成正在运行。

### 命令

```bash
npm run pipeline -- status            # 全貌
npm run pipeline -- status --brief    # 两三行，给指挥官定时看
npm run pipeline -- log --tail 20
npm run pipeline -- providers         # 哪些提供方现在能用
npm run pipeline -- funnel            # 每个来源的条目各在什么状态，悬空的原因
npm run pipeline -- item x-post-123   # 一条内容卡在哪一步、为什么
npm run pipeline -- test-provider kimi-code --by codex
npm run pipeline -- test-provider codex-cli --image /path/to/photo.jpg --by codex

npm run pipeline -- target 100 --by codex --reason "先每天 100 条"
npm run pipeline -- route review kimi-code --model k3.1-pro --by codex --reason "用 Kimi 闲置额度"
npm run pipeline -- route translate codex-cli --model gpt-6.1-terra --fallback anthropic-api --fallback-model claude-haiku-5-5 --by claude-code
npm run pipeline -- start --by codex
npm run pipeline -- pause --by claude-code --reason "额度快用完"
npm run pipeline -- note "Lucy 说周末前别动安全复核" --by claude-code
```

环节：`prefilter`（预筛）、`review`（合并审核）、`safety`（安全复核）、`translate`（翻译）、`translationCheck`（翻译检查）。默认全部走 Codex 订阅：预筛和审核用 gpt-5.6-luna，安全复核和翻译检查用 gpt-6-astra，翻译用 gpt-5.6-terra。用 ChatGPT 账号登录的 Codex 只能用它列出的模型（2026-11-06 为 gpt-6-astra、gpt-5.6-sol、gpt-5.6-terra、gpt-5.6-luna），gpt-6.1-sol 和 gpt-6-luna 会被拒绝；换模型前先 `test-provider codex-cli --model <名字>`。

## 条目状态（funnel）

每条采集到的内容只能处在下面一种状态，`npm run pipeline -- funnel` 按来源统计，`item <id>` 看单条：

- **线上 / 已下架**：以数据库为准。
- **已排除**：有明确的「不发布」结论，记着是哪个环节、什么原因。例如编辑审核拒绝或暂缓、图片审核判为不符或存疑、画面露骨、2.0 审核排除、正文超过 30,000 字符、来源已停用（YouMind）、原帖已删。模型的暂缓和存疑针对的是这一版内容，结论永久缓存、不再送审，也没有人工环节，所以算最终结论；内容或来源一变，就会重新审核。
- **排队中**：某个自动环节之后会处理它，例如等编辑审核、等图片审核、等发布名额。
- **悬空**：没上线、也没被排除，但没有任何环节会再处理它。这违反「每条都有结论」的规则，所以单独计数。

判定按每日流程的顺序，复用流程本身的判断函数（编辑审核结果、`automaticReviewEligibility`、`libraryIssue`、`filterXAvailability`），所以和流程不会各说各话。任何环节给出的最终「不发布」都优先于可以刷新的来源复查。

2026-11-07 第一次统计有 366 条悬空。同一天修掉了其中大部分：模型暂缓和图片存疑改记为已排除；正文超过 30,000 字符的，在编辑审核前就排除，不再写「待人工」；带图的 X 出图帖子只挂了 ChatGPT 之类的聊天工具名时，不再误判成纯文本。未上线 X 草稿的原帖复查过期后，定时维护复查（PR #264）会按编辑队列顺序给草稿至少 50 个复查名额，所以记为排队中；队列在每个书架里按发帖时间从新到旧排，老草稿会排在更新的草稿后面。

`status --brief` 显示最近一次统计的悬空和排队数量。每日日报（以及 `report`）会重新统计并保存快照；当天有新进入悬空的条目，日报结论会写「有问题」。

还不覆盖历史补库 campaign 里尚未上线的条目，它们的状态在各 campaign 目录和数据库队列里。

## 指挥官怎么工作

你对任何一个 agent 说「开始，每天抓 100 个」，它应该：

1. `status` 看当前状态和路由；
2. `target 100 --by <自己>`，必要时 `route …`，再 `start --by <自己>`；
3. 用一两句话告诉你改了什么、预计什么时候能看到结果。

你问「电脑上有没有在跑的管线、跑得怎么样」，任何一个 agent 只需要 `status --brief`，必要时再看 `log`。

盯任务的节奏要省 token：

- 不轮询。后台进程出错、停摆或连续被拒时，通过已有的监控 Worker 发邮件报警，指挥官不需要每分钟去看。
- 如果你要求它「盯着」，用低频定时检查：每 2–4 小时一次 `status --brief`，只有异常时才展开看 `log`。
- 指挥官自己不跑审核，也不把原始内容读进对话；它的上下文只装状态和记录。

## 后台进程

第一版已上线（2026-11-06）：`ingest/worker.ts` 由 launchd 保活（`dev.prompix.worker`，开机自启，退出后自动重启），代码从主仓库目录运行。每分钟写一次心跳，按到期顺序一次只跑一个任务，任务结果记进 `events.jsonl` 和 `status`。

- **来源维护复查**（每天日本时间凌晨 2:45，失败 30 分钟后重试）：带上已发布 ID 做 X 来源复查，并刷新 ClawHub 核验。每次发布都要检查这两项核验。ClawHub 核验 24 小时内有效。X 来源按发帖时间分级：核验时发帖不满 7 天的，核验 24 小时内有效；已满 7 天的，核验 7 天内有效。每次维护都会在核验到期前 12 小时重新复查。作者大多在发帖后不久删帖，所以老帖每周查一次就够，每天的复查开销从约 $0.5 降到几美分；代价是老帖被删后，最多 7 天才下架。X 花费账本给复查预留的额度也按这个算：不满 7 天的帖子按每天查两次预留，满 7 天的按每 6 天查一次预留（`maintenanceRunway`）。原来一律按每天两次全量预留，每天约 $0.9，算上剩余天数会超过每月 $20 的上限，导致新内容的搜索全部被拒。还没上线的草稿也会顺带复查：名额按编辑审核还剩的容量算，维护复查时至少保留 50 条（一次 twitterapi 请求），按编辑队列顺序取，避免当天编辑名额用完后草稿的来源核验一直过期。确认原帖已删的条目，立即在数据库里下架，不等下一次发布。一次要下架超过 50 条时拒绝执行并报错，因为这更可能是接口故障。这项任务属于安全职责，不管期望状态是运行、暂停还是停止都会执行。
- **每日采集发布**（期望状态为「运行」时，每天日本时间凌晨 3:00 跑一轮；失败后每 30 分钟重试一次，每晚最多 3 次，单次最长 3 小时。第 3 次也失败，或者外置硬盘没接上，会立刻发告警邮件。Mac 关机错过的话，开机后补跑）：在单独的进程里跑 `ingest/daily.ts --publish`：采集、审核、翻译和发布。图文比例和全部发布前检查不变。2026-11-07 起：
  - **X 采集**（`ingest/x-nightly.ts`）：按试跑验证过的搜索规则，搜日本时间**前天**一整天的帖子（延后 2 天，让点赞沉淀、删帖先消失、回复里的提示词补齐）。精选创作者除了线上作品多的作者，还加上最近两周被一轮审核通过至少 2 次、人像不超过一半的作者（最多 24 人）。每天最多 300 条；某条规则搜不满自己的份额时，没用完的名额按「写法、精选创作者、用途、模型、探索」的顺序让给还有帖子的规则，每条最多再翻 2 页。光标记在内容目录的 `x-nightly/cursor.json`，错过的日子下次最多补 3 天。没写「Prompt:」的帖子交给 `review` 路由找提示词，结果写进 `x-excerpt-reviews.json`。写着「提示词在回复里」的帖子（含「リプ欄」「见评论区」「See reply」等写法），每晚最多读 60 个作者回复串，回复里的提示词走原来的回复串收录，发布前要先过来源复查，所以通常晚一晚上线。原来的搜索计划、线索队列和官方补充采集不再在每晚流程里运行。
  - **X 新帖只过一轮审核**（`ingest/review-daily.ts`，走 `review` 路由）：没上线的 X 帖子不再走编辑审核、图片审核和 2.0 审核，改为 `review-pass.ts` 的一轮审核，按上面的审核标准判断，一次给出卡片、标签、尺度和模型名。每晚最多审 240 条，从新到旧；结果按帖子和来源版本存在 `review-pass/outcomes/`，内容不变不重审；判定失败的下一晚再试一次。人像和人物最多占当晚通过的一半，多出的留到以后。被拒的记在 `review-pass/rejected.json`，来源维护不再为它们花复查额度。prompts.chat 和已上线条目仍走原来的编辑审核和 2.0 闸。
  - 其余和旧定时任务的不同：
  - 翻译走管线的 `translate` 路由（`PROMPIX_TRANSLATION_PROVIDER=pipeline`），不再写死 Codex gpt-6-luna。
  - 不处理历史补库 campaign，因为那里的条目没有经过 2.0 审核。
  - 发布前多一道 2.0 审核闸（`ingest/enrichment-daily.ts`，走 `review` 路由）。新条目必须有针对当前内容的有效审核，尺度也必须定得下来：涉及未成年人不安全或不确定的、explicit、unknown 一律不发布；拒答的永不再送审；还没审到的顺延到下一个时段。每次排除写一行到内容目录的 `enrichment/exclusions.jsonl`。
  - 已上线条目内容没变的，保留它 2.0 审核的结果。从来源重建时丢掉的字段补回来；尺度取两者中更严的，但 unknown 不会覆盖已经判定过的尺度。内容有改动的重新审核，审核通过前继续用线上原版。
- **内容范围**（2026-11-07 起）：只收 X 和 prompts.chat 上的图片、视频和文字提示词。Skill 来源（官方和作者的仓库、ClawHub、从 X 发现的 Skill）和网页类都已停用，已上线的 128 条 Skill 和 7 条网页类全部下架，写进下架名单。浏览页的 web 分组也已删除，旧版 App 请求 `collection=web` 时返回空列表。
- **发布不设每日总数上限**（2026-11-07 起）：审核通过的带图作品全部发布，数量由前面的抓取量决定。纯文字仍按比例放行：同一个 UTC 日里，每发布 4 条带图作品，才能发布 1 条新的纯文字。数据库激活时也不再检查每天 100 条。
- **每日供给上限**（按四个 UTC 时段累计放开）：X 每天最多抓取 300 条完整帖子（`PROMPIX_X_ACQUISITIONS_PER_DAY`，上限 1000，每条约 $0.00015；owner 2026-11-07 从 600 改为 300）、搜索最多 200 次请求（`PROMPIX_X_SEARCH_REQUESTS_PER_DAY`，上限 400）。2026-11-07 的试跑里，按严格审核只有约 11% 的帖子能发布，200 条撑不起每天 100 条；放宽审核后再按试跑结果调整。prompts.chat 只在仓库有新提交时才重新下载整份 CSV，否则沿用上次的快照。
- **每日日报**（每天日本时间早上 8:30）：汇总之前 24 小时，也就是当晚那一轮，通过监控 Worker 的 `/report` 发到告警邮箱。日报第一行写结论：正常完成，或者具体有什么问题（最后一次运行失败、全天没有一次成功的采集发布、线上数据读不到）。后面依次是线上新增和下架数量（以数据库为准，对照每天目标）、2.0 审核和译文复核排除了多少、每个任务的运行次数、各次结果和用时、成本估算（模型 API 按标价和实际 token 数算，X 按花费账本算，Codex 订阅只记调用次数）。后台进程还没跑过每日采集的日子不发。手动预览或补发用 `npm run pipeline -- report [--since 时间] [--send]`。
- **花费上限**：Anthropic API 每个 UTC 日最多 $2（`anthropicDailyCapUSD`），按当天日志里所有 Anthropic 调用的估算花费累计。达到上限后，走 Anthropic 的路由一律报「不可用」，这一步停下（或者交给另一个备用），日报里写明。2026-11-07 起译文不再单独复核，翻译之后直接靠校验器把关。
- **加跑一轮**（`npm run pipeline -- intake --by <名字> [--import-trial <试跑编号,…>]`）：后台进程在当前任务结束后马上跑一轮采集发布，不占当晚 3 点那一轮。`--import-trial` 把这些试跑搜到的帖子按原抓取时间写进收录目录，找提示词后和当晚的帖子一起审核发布。来源核验沿用试跑时的抓取，只在 12 小时内有效，所以要在试跑后半天内跑；过期的要等来源维护复查后才能发布。
- **新流程试跑**（`npm run pipeline -- trial --by <名字>`，由后台进程执行，不发布）：按新的搜索策略（`ingest/x-search-rules.ts`：按用途 35%、按模型 15%、精选创作者 25%、按 Prompt 里常见的写法（构图、光线、相机等）20%、探索 5%；图片 70%、视频 30%；点赞至少 20 条；每个创作者每天最多 3 条；不搜 Sora）搜索最近 24 小时的 X 帖子。之后走同一套收录和媒体转存，再做一轮审核和打标（`ingest/review-pass.ts`），审核按下面的标准判断；人像和人物类最多占当天的一半（2026-11-07 owner 从 35% 放宽）；最后用 `translate` 路由翻译成 9 种语言。结果和统计写在内容目录的 `trials/<时间>/` 下：`summary.json` 是总览，`results.json` 是逐条结果，另有缩略图。
- **找提示词**：帖子里没写「Prompt:」这类标记的（第一次试跑里占 62%），交给 `review` 路由的模型判断有没有完整提示词，有的话把原文照抄出来（`ingest/prompt-locate.ts`）。只有和作者原文对得上的才收录，正文一律从作者原文里截取，模型改不了一个字。试跑可以用 `trial --replay <试跑编号>` 拿上一次搜到的帖子重审，不再花 X 的搜索费；也可以用 `trial --day 2026-11-02` 搜日本时间某一整天，模拟那天的每日流程。
- **审核标准**（一轮审核，2026-11-07 第一次试跑后按 owner 意见放宽）：默认发布，只有明显不合格才拒，拿不准就发。拒绝理由：提示词被截断或离开原帖看不懂；只有几个词；没有生成结果；结果明显是另一个主题；结果明显失败；要关注、私信、转发或付费才给提示词，或整帖是课程广告；大水印盖住主体或拼了不相关的作品；针对具体真实人物；露骨、性暴力或胁迫，或涉及未成年人不当内容。不算拒绝理由的：要用户上传自己照片或参考图的提示词、作者的错别字、视频抽帧里没看到某个情节、小瑕疵、小的工具水印和署名、提示词本身要求的宫格或对比图、生成的商品广告片。内衣、泳装、性感造型不拒，标成「擦边」，默认不显示，用户打开开关才看得到。未成年人判为「不安全」的不发布；判为「拿不准」的只在同时带擦边造型时不发布（owner 2026-11-07 决定，单独的「拿不准」不再拦），而且只有画面或文字里有具体迹象（孩子样貌、校服、写明年龄、child/kid 等）才算「拿不准」，年轻感的成年人、girl 这个词、动漫画风或时尚大片都不算。尺度判为「判不准」或「露骨」的不发布。模型名统一成一种写法，判断不了的写 Unspecified。
- 密钥从 `~/.config/prompix/*.env` 读取，和旧定时任务用同一组文件。
- 子进程（每日流程和它调用的 wrangler）不认后台进程自己加载的系统证书，所以后台进程启动时把系统钥匙串里的根证书导出到控制目录的 `system-roots.pem`，再通过 `NODE_EXTRA_CA_CERTS` 传给子进程。
- 和旧任务共用内容目录的 `daily.lock`，两边不会同时运行。
- 更新代码后执行 `npm run pipeline -- worker restart`。

### 接下来


- 常驻在这台 Mac 上，用 launchd 保活；每轮先读 `config.json`，所以改路由、改目标、暂停都在下一轮生效，不用重启。
- 沿用 Supabase 里已有的任务队列；每个环节有自己的并发数。审核按批处理：订阅命令行每次调用打包 6–10 条，并行 3–4 个，用来摊薄每次调用约 1 万 token 的系统提示开销（Codex 实测）。
- 每个提供方单独统计 token 和限流；遇到 `rate_limited` 先退避，持续受限时暂停该环节并记录，等指挥官或你决定是否换路由。
- 每个环节可以配一个备用路由（`route … --fallback <提供方>`，`--fallback none` 取消）。主路由报 `unavailable`（未登录、无此模型、没有余额）或 `rate_limited`（限流、额度用完）时，这一次调用改走备用，并在记录里写一条 `route.fallback`。拒答、输出不合格等针对内容本身的结果不会交给备用模型。调用记录写的是实际回答的模型。
- 保留现有的安全闸：许可和署名检查、去重、来源新鲜度、尺度标签（暗示性和未定的内容默认隐藏）。没有人工环节：判定全部由流水线完成，拿不准的一律不发布。
  - 涉及未成年人：凡带性暗示、暴露，或把未成年人当作可替换模特的，一律拒绝；判断不了年龄又涉及人物尺度的，也不发布。
  - 真人：按尺度规则自动判定。原来的「只用本人照片」提示（`ownLikenessOnly`）随 `inputs` 一起在 2026-11-07 停用。
  - 每次排除都记录条目 ID、环节、原因和模型。条目以后重新采集或复查时，可以再判一次。
- 去掉旧管线里没有安全作用的等待：每天 4 次定时、两条线共用的锁、发布窗口和图文比例、每次调用新起进程的额外批次、全局「5 次不明就停」。
