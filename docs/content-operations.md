# 内容运行手册

## 本机运行

- 任务：`dev.prompix.collect`，每天本机时间 08:00；当前 Mac 为 Asia/Tokyo。
- 安装／升级：在已校验的 checkout 运行 `python3 scripts/install-scheduler.py`。脚本先安装独立运行目录，再原子切换 runtime 链接和重新注册 launchd；只有注册成功后才执行旧运行目录的保留策略。
- 手动执行：`launchctl kickstart gui/$(id -u)/dev.prompix.collect`。
- 状态：`launchctl print gui/$(id -u)/dev.prompix.collect`。
- 日志：`~/.local/share/prompix/daily.log`，超过 1 MB 保留一份 previous。
- 结果：`~/.local/share/prompix/content/status.json`，包含逐来源成功／失败、版本、媒体失败列表。
- 本地预览：`npm run daily`；人工发布：`npm run daily -- --publish`。
- 下架：`npm run remove -- <id> <reason>`，再发布。不得将包含第三方内容的 JSON、媒体或日志提交到仓库。

launchd 是用户任务，须登录该用户；关机时不会运行。内容进程锁避免并发，崩溃后的失效锁一小时后可由内容命令恢复。升级前确认任务未在运行；安装器不会自行删除内容锁。安装器把实际 Node、Wrangler 和 Git 的可执行目录写入后台 PATH；使用 Homebrew keg-only Node 时同样可被上传工具的 shebang 找到。

运行目录位于 `~/.local/share/prompix/runtimes/`。安装器与 Python 启动器共用 `runtime.lock`：采集从解析 runtime 链接到子进程退出期间持有共享锁，升级／清理持有独占锁，忙时退出并保留原目录。不要删除锁文件，也不要直接从历史运行目录启动 Node；日常运行使用上面的 launchd 命令或 `run-daily.sh`，从开发 checkout 调试仍可使用 `npm run daily`。

成功升级后只保留 `runtime` 当前目录和 `runtime.previous` 指向的上一个已激活目录。清理只识别 runtimes 下数字命名、结构匹配的 Prompix 目录；未知目录、目录软链接、内容、日志及凭据均不清理。由旧启动器首次迁移时只安装锁保护、暂不删除历史目录；下一次成功升级才收敛到两个版本。安装或 launchd 注册失败时不做历史清理，恢复旧链接与启动文件，并尝试重新注册原任务；恢复失败时也不会删除仍被活动链接引用的新目录。此策略不清理内容版本、媒体和发布回滚数据。

保留策略的隔离测试：`python3 -m unittest discover -s scripts -p 'test_scheduler.py' -v`。测试仅使用临时目录和模拟 npm／launchd，不安装生产任务或执行真实清理。

公开 GitHub 来源使用本机 Git 的 `ls-remote` 解析默认分支，再按不可变 commit 下载文件；运行环境须有 Git。这样不依赖共享出口的匿名 REST API 额度。仓库与文件名均使用显式白名单，解析或网络失败仍保留上次快照。

### X 发现与原生草稿

X 搜索现在聚焦五位已收录创作者，并检索英文、中文、日文的 Prompt 标记；仍限每天一次请求、最多10条，不抓网页、不自动分页或重试。查询、字段集、端点、排序与数量共同形成指纹，增量游标写入 `x-state.json.cursors[指纹]`。历史无指纹游标不会套到新查询；全局 `day` 名额独立保留，切换查询不能增加当日请求。

`x-search-attempts/YYYY-MM-DD.json` 在请求前记录无凭据的查询身份；成功快照先保存，再推进该查询游标。新快照的 `request` 与 `coverage` 区分长文、entities、关联媒体与真实作者资料覆盖；0表示响应未提供，不能推断原帖确实没有。部分API错误、格式损坏、重定向或保存失败消耗当天尝试，不自动重发。字段别名继续等待下一次正常预算内请求验证。

升级运行器后，每次 daily 都会读取已有 X 缓存，按原帖 ID 去重，将有明确提示词边界和可提取正文的记录写入 `candidates/x-native.json`；不新增付费请求，不追踪外链或线程。常见Markdown／emoji和日文标记可识别；只按当前正文的API entities展开明确链接，只有确证属于本帖附件的尾部短链占位才能移除。模态不能确定时保持待审，不能把所有泛用Prompt归入文本。长帖优先使用完整 note 正文；未标明正文边界、截断、代码围栏未结束、仅含链接或正文仍含未展开短链时保留具体阻塞原因。捕获原帖 URL、作者数字 ID、可用真实资料和对应附件地址，许可如实标为 `Unspecified`，不把数字帖子 ID 伪装成 Git commit。

查看 `status.json.sources["x-intake"]` 的 `discovered/drafted/blocked/publicationBlocked/reviewedDrafts` 与 `reasons`；`x-intake/status.json` 保留逐帖追踪及损坏快照记录。没有新的 X 请求也会重建这些报告。`npm run review -- x-post-<id> /absolute/path/editorial-metadata.json` 可以准备元数据，返回 `draft-awaiting-source-review`。原生 X 目前仍等待来源与发布接入，不参与自动模型审核或公开目录；编辑文案不能解除该门槛。详情与字段兼容边界见[采集说明](../ingest/README.md#native-x-intake)。

## 凭据与费用

X 凭据从 `~/.config/prompix/x.env` 加载，文件权限 0600，只包含变量 `X_BEARER_TOKEN`。无需把 Key 发到聊天、App 或 GitHub。账号充值／付款方式由用户完成，自动充值没有启用。

当前 X 发现策略最多每天 10 条返回帖子、一次请求；[官方按量价格](https://docs.x.com/x-api/getting-started/pricing)列出 Posts Read 为每条 $0.005，预计上限约 $0.05／天（不包含未来价格变化或另行启用的资源）。实际以控制台账单为准。失败尝试也占用本机当天名额，避免异常重试花费；人工重试前检查 `x-state.json` 和控制台用量。

Cloudflare 上传显式使用 `services/content/wrangler.jsonc` 中指定的项目账号，避免登录多个账号后后台任务无法选择。使用本机已授权的 Wrangler OAuth；过期后若刷新失败，重新 `wrangler login`，无需将 OAuth 凭据复制到项目。Worker 通过 R2 binding 读取，不携带发布密钥。Cloudflare 套餐按当前账号计费，不默认启用付费增值产品。

| 表现 | 处理 |
|---|---|
| X HTTP 402 | 额度不足；完成付款设置／充值后重试，其他来源无需停机 |
| 单来源解析失败或空结果 | 保留上次快照，检查上游 README／CSV 格式，再修改合成测试 |
| 媒体来源不在白名单 | 检查真实公开链接后再显式补充，不能开放任意 URL 抓取 |
| 上传／验证失败 | latest 保持旧版本；检查网络、Wrangler 登录和存储空间 |
| App 更新失败 | 保留已验证缓存；在 App 的更新状态或设置中手动重试，并检查线上清单和 `npm run check:deployment` |
| App 仍显示 68 条且没有作者资料 | 先核对实际内容版本和更新状态。旧缓存可能缺少结构化作者；0.3.1 的未筛选首页仍保留创作者入口，并说明更新需求。不要为此清空收藏、草稿或卸载 App |
| 不需要定时采集 | `launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/dev.prompix.collect.plist`；内容服务仍可读 |

### 0.3.1 客户端更新与排查

安装新 App 不等于手机已完成内容更新。启动时先读取已验证的本机目录，再联网检查线上清单；原 68 条缓存没有结构化作者元数据时，旧界面会直接隐藏创作者区，这是已确认的入口缺失原因。0.3.1 在未筛选首页保留入口，另显示检查、下载、安装或失败状态。不能仅凭旧缓存仍在就断言后台没有发布，也没有证据把手机的全部更新延迟归因于旧逐字节循环。

成功检查后的自动尝试间隔为 15 分钟；失败后缩短为距上次尝试 30 秒，此后的前台事件或非强制刷新才会触发下一次请求。没有到点自行执行的重试定时器；下拉刷新和显式重试可立即发起，取消任务也允许下次触发立即再试。已有请求运行时不会再启动第二个。节流状态只保留在当前 App 进程内。

客户端请求超时参数为 60 秒，不是整个刷新过程的硬截止时间。下载按块累积并限制清单 32,000 字节、目录 10,000,000 字节；压缩响应或未知总长度使用不确定进度，直到接收完成。之后在主 actor 之外完成哈希和目录校验，再执行原子安装。网络、完整性校验或安装失败继续保留旧内容及个人数据；排查时应区分线上版本、当前设备缓存版本与正在进行的更新，不将条目数本身当作安装成功的凭证。

## 回滚与恢复发布

发布版本保存在 R2 和本机 releases 下。使用下面的回滚命令，不直接上传旧 manifest；不要为恢复一次抓取而清空收藏或整个内容目录。

1. 从本机 `releases/<version>/manifest.json` 选择目标，执行 `npm run rollback -- <version>`。默认仅演练：读取线上当前与目标目录、核对校验和与条目数，合并目标／当前／本地全部下架 ID，生成独立的 `rollback-*` 版本；不切换线上、不改变下架记录或发布状态。
2. 确认 `rollback-status.json` 的目标和数量后，运行 `npm run rollback -- <version> --publish`。检查旧版本媒体可读取，上传并复核新目录，最后激活清单；上传失败记录到 `rollback-status.json` 和 `operations/rollback-*.json`。
3. 回滚激活前写入 `publication-hold.json`。下一次每日任务仍采集候选，但跳过发布，状态中带 `publicationHold`。不手动删除此文件；这样有歧义的上传响应也不会让次日任务覆盖修复版。
4. 修复采集或编辑问题后，执行 `npm run daily` 查看候选，再运行 `npm run daily -- --publish --resume-publishing`。只有线上激活校验通过后才清除 hold。最后运行 `npm run check:deployment`。

采集、回滚、下架共用同一进程锁，避免本机发布交错。恢复发布会把线上有效下架记录合并到本地，因此恢复较旧备份不会让已下架条目重新出现。暂停发布期间的紧急下架：先 `npm run remove -- <id> <reason>`，再以当前线上版本作为回滚目标执行第 1、2 步。客户端下次更新会应用下架记录；保存在用户剪贴板或已经导出的内容无法远程撤回。

回滚要求本机目标清单仍在且对应远程目录可验证。丢失本地清单、媒体失效或当前版本无法校验时会停止，不猜测版本、不删除远程媒体。当前命令用于已建立的生产内容库；首次初始化仍通过经过检查的发布流程执行。

## 编辑发布

候选保存在 `candidates/`，编辑记录保存在仓库外的 `editorial.json`。用 `npm run review -- <candidate-id> /absolute/path/editorial-metadata.json` 写入标题、用途、示例、标签、封面和可选排序；字段说明见 [采集说明](../ingest/README.md)。原始正文与作者保持不变。编辑记录绑定正文指纹，来源正文变化后需要重新确认。

轻量增量审核可以在升级运行器后通过 `~/.config/prompix/editorial.env` 中的 `PROMPIX_EDITORIAL_PROVIDER=codex` 启用；固定使用 `gpt-5.6-luna`，每个 UTC 日最多一次请求、三条完整候选，总输入不超过 16,000 字符。请求前写入持久账本，失败或响应不明确时当天不重试。模型只整理标题、用途、使用建议、标签和封面文案，不改正文、来源、创作者、许可或媒体地址；拒绝和暂缓决定按正文指纹缓存。新批准内容继续走既有翻译、媒体与发布校验。普通 staging 不调用审核模型。详细开关、文件位置和状态字段见[采集说明](../ingest/README.md)。

社区文本默认不发布，网页还须有作品链接与真实预览。图片条目需要核对正文与所选图片，不能假定上游首图就是对应结果；可通过 imageURL 指定已检查的图片，或使用 imageURLs 指定 1–8 张经逐张核对的有序图集，首张成为封面。新增该字段前先升级每日运行副本；所有图片完成镜像才发布该条目。编辑命令只准备内容，下一次 daily 发布才生效。原创内置目录目前 30 条（文本、图片、网页），不使用旧生成脚本覆盖维护。

视频历史补录使用 `npm run backfill:video`：仅从已有白名单仓库的固定 2026-03-25 commit 暂存草稿，不调用 X、不下载媒体、不发布。可用 `PROMPIX_CONTENT_DIR` 指定独立的仓库外复查目录；未指定时进入正式内容目录的单独 archive 候选文件。逐条检查实际视频和代表性封面并应用编辑记录后，daily 才纳入完整视频目录，不再限制为 12 条。历史案例不宣传为当日热帖；当日采集仍独立运行，和归档重复的原帖优先使用当前正文。当前条目即使缺少视频或封面也保留为草稿，只有正文指纹相同时才可使用已审核的完整归档案例；正文变化后不得复用旧审核，补充编辑文案也不能代替缺失的实际媒体。未补录时不加入历史案例，状态报告标记 archive 为 `not-staged`；补录后为 `staged`，不代表已发布。具体 commit 和边界见采集说明。

## 完整目录与实际增量

`status.json` 的 `counts.candidates/reviewed/eligible` 仅统计社区条目；`bundled` 单列原创，`prepared` 是最终去重后的准备目录，`published` 仅在线上激活或相同版本复核成功后填写。各阶段均按 text/image/video/web 计数，未执行阶段为 null，`mediaFailed` 单列媒体失败。`changes.added/removed` 根据 `comparisonVersion` 对应的已校验线上目录计算；重排或同版运行不能算新增。

全库移除按来源／模态的数量配额，编辑排序仍生效。发布前的全部内容必须通过当前正文指纹审核、结构与内容规则、镜像和去重。超出 v1 的 1,000 条或 10 MB 时停止发布并保留旧版，不能为了维持任务成功而静默裁掉内容。

这里的大小门槛是UTF-8解码目录的10,000,000字节，HTTP压缩不能绕过。新release以紧凑JSON写入；旧release重试保留已有字节、SHA和发布时间，即使重新编码会更小也不改写。发布、staging、远程读取、回滚与部署检查共用这个上限；清单另限32,000字节。每日处理可能已上传可复用的内容寻址媒体，但超限时不上传目录或激活清单。回滚的新目录及本地已有目录均须在媒体探测、上传、hold或latest变更之前通过容量检查。超限失败应演进协议或修复输入，不手动改大单个路径的限制。

最终组装保留线上已校验版本中的所有既有 ID，除非明确写入下架记录。上游修改尚待审核、源条目暂时缺失或新媒体下载失败时，继续发布旧的完整快照（正文、署名、镜像及译文）；不会把未审新正文附到旧预览上。新来源的重复内容不能替换用户已收藏的旧 ID。`retainedPrevious` 按原因报告实际保留数，`changes.removed` 不应出现无下架依据的既有条目。
