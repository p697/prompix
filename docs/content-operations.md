# 内容运行手册

## 本机运行

- 任务：`dev.prompix.collect`，每天本机时间 02:00／08:00／14:00／20:00；当前 Mac 为 Asia/Tokyo。
- 安装／升级：在已校验的 checkout 运行 `python3 scripts/install-scheduler.py`。脚本先安装独立运行目录，再原子切换 runtime 链接和重新注册 launchd；只有注册成功后才执行旧运行目录的保留策略。
- 手动执行：`launchctl kickstart gui/$(id -u)/dev.prompix.collect`。
- 状态：`launchctl print gui/$(id -u)/dev.prompix.collect`。
- 日志：`~/.local/share/prompix/daily.log`，超过 1 MB 保留一份 previous。
- 结果：`~/.local/share/prompix/content/status.json`，包含本次 `runID`、`state`、逐来源成功／失败、版本和媒体失败列表。须同时核对本次起止时间、launchd退出码和日志，不能只看 `published`。
- 存储：上述 content 路径现链接到外接 SSD 的 `Prompix-Codex/Data/content`；保持 SSD 挂载，base 与 runtimes 仍留在本机真实目录。
- 本地预览：`npm run daily`；人工发布：`npm run daily -- --publish`。
- 下架：`npm run remove -- <id> <reason>`，再发布。不得将包含第三方内容的 JSON、媒体或日志提交到仓库。

launchd 是用户任务，须登录该用户；关机时不会运行。内容进程锁避免并发，崩溃后的失效锁一小时后可由内容命令恢复。升级前确认任务未在运行；安装器不会自行删除内容锁。安装器把实际 Node、Wrangler、Git 和 GitHub CLI 的可执行目录写入后台 PATH；使用 Homebrew keg-only Node 时同样可被上传工具的 shebang 找到。

运行目录位于 `~/.local/share/prompix/runtimes/`。安装器与 Python 启动器共用 `runtime.lock`：采集从解析 runtime 链接到子进程退出期间持有共享锁，升级／清理持有独占锁，忙时退出并保留原目录。不要删除锁文件，也不要直接从历史运行目录启动 Node；日常运行使用上面的 launchd 命令或 `run-daily.sh`，从开发 checkout 调试仍可使用 `npm run daily`。

成功升级后只保留 `runtime` 当前目录和 `runtime.previous` 指向的上一个已激活目录。清理只识别 runtimes 下数字命名、结构匹配的 Prompix 目录；未知目录、目录软链接、内容、日志及凭据均不清理。由旧启动器首次迁移时只安装锁保护、暂不删除历史目录；下一次成功升级才收敛到两个版本。安装或 launchd 注册失败时不做历史清理，恢复旧链接与启动文件，并尝试重新注册原任务；恢复失败时也不会删除仍被活动链接引用的新目录。此策略不清理内容版本、媒体和发布回滚数据。

保留策略的隔离测试：`python3 -m unittest discover -s scripts -p 'test_scheduler.py' -v`。测试仅使用临时目录和模拟 npm／launchd，不安装生产任务或执行真实清理。

### 状态与失败判读

采集取得内容锁后先写 `state: running`，再进行来源请求、模型调用或发布恢复。开始写入失败立即停止主体，并尽力移除旧状态；竞争进程未取得锁时不修改现有状态。终态在释放内容锁前保存为 `succeeded` 或 `failed`；`succeeded` 只表示这次运行正常结束，不代表所有来源成功，也不代表已发布，仍须看各阶段、`publicationHold` 和 `published`。

终态写入失败时，文件会停留在本次 `running`，日志仍输出原始错误、独立的 `statusWriteError` 和结束时间，进程非零退出。若连开始写和删除旧文件都失败，旧成功记录仍可能存在，日志会包含 `statusInvalidationError`；强制杀进程也不能保证终态。解锁失败单独记录 `unlockError`，不能覆盖原始业务异常；它发生在终态保存后，因此文件可能仍显示 `succeeded`，但日志和退出码判为失败。已经发布但状态保存失败时保留 `published: true`，不伪造回滚。故障后先核实活进程和同一 `runID` 的日志，不据一份状态文件重试或清零付费账本。

故障回归 `node --import tsx --test ingest/daily-status.test.ts` 使用隔离临时目录与真实内容锁，注入开始／结束写失败、业务失败、解锁失败、只读删除失败和竞争运行；不访问来源、模型或生产数据。运行器启动前、锁创建失败等仍走已有 CLI／launchd 错误路径，不能从根状态文件推断它们已被记录。

公开 GitHub 来源使用本机 Git 的 `ls-remote` 解析默认分支，再按不可变 commit 下载文件；运行环境须有 Git。这样不依赖共享出口的匿名 REST API 额度。仓库与文件名均使用显式白名单，解析或网络失败仍保留上次快照。

2026-10-11 已在付款设置完成后通过已安装的 launchd 任务验证 X：成功获取 10 条发现记录并持久化增量游标。原帖保存在内容目录的 `x-discovery/YYYY-MM-DD.json`；一次搜索成功不代表这些帖子已出现在 App。后续运行保留当天请求名额，不重复付费读取。搜索是否成功须检查 `status.json` 的 `sources.x`，不能只看任务退出码。

查看 `status.json.sources["x-intake"]` 的 `discovered/drafted/blocked/publicationBlocked/reviewedDrafts` 与 `reasons`；`x-intake/status.json` 保留逐帖追踪及损坏快照记录。没有新的 X 请求也会重建这些报告。`npm run review -- x-post-<id> /absolute/path/editorial-metadata.json` 可以准备元数据，返回 `draft-awaiting-source-review`。原生 X 目前仍等待来源与发布接入，不参与自动模型审核或公开目录；编辑文案不能解除该门槛。详情与字段兼容边界见[采集说明](../ingest/README.md#native-x-intake)。

## 凭据与费用

X 凭据从 `~/.config/prompix/x.env` 加载，文件权限 0600，只包含变量 `X_BEARER_TOKEN`。无需把 Key 发到聊天、App 或 GitHub。账号充值／付款方式由用户完成，自动充值没有启用。

当前本机 X 搜索预算为每日 12 请求／600 帖，来源复查另为 2 请求／200 帖；所有定时和手动运行共用持久账本。请求前即预留，失败或结果未决不清零、不自动重试；实际费用以 X 控制台为准，不能沿用早期一次10帖的预算估算。

Cloudflare 上传显式使用 `services/content/wrangler.jsonc` 中指定的项目账号，避免登录多个账号后后台任务无法选择。使用本机已授权的 Wrangler OAuth；过期后若刷新失败，重新 `wrangler login`，无需将 OAuth 凭据复制到项目。Worker 通过 R2 binding 读取，不携带发布密钥。Cloudflare 套餐按当前账号计费，不默认启用付费增值产品。

官方 Skill 的完整文件清单通过本机已登录的 `gh api --hostname github.com` 读取白名单仓库的固定 commit tree。同仓库同 revision 共用一次请求；不再使用 GitHub 匿名 API 配额，不把 CLI 凭据写入配置或日志。后台须能找到 `gh` 且其 GitHub 登录有效。命令禁止交互，60秒截止、7 MB响应上限；请求、解析或完整性验证失败保留上次完整候选，不能把只下载的两个核心文件当作完整包清单。修复登录后由下一次每日任务重试，无匿名回退。

### 0.3.1 客户端更新与排查

安装新 App 不等于手机已完成内容更新。启动时先读取已验证的本机目录，再联网检查线上清单；原 68 条缓存没有结构化作者元数据时，旧界面会直接隐藏创作者区，这是已确认的入口缺失原因。0.3.1 在未筛选首页保留入口，另显示检查、下载、安装或失败状态。不能仅凭旧缓存仍在就断言后台没有发布，也没有证据把手机的全部更新延迟归因于旧逐字节循环。

成功检查后的自动尝试间隔为 15 分钟；失败后缩短为距上次尝试 30 秒，此后的前台事件或非强制刷新才会触发下一次请求。没有到点自行执行的重试定时器；下拉刷新和显式重试可立即发起，取消任务也允许下次触发立即再试。已有请求运行时不会再启动第二个。节流状态只保留在当前 App 进程内。

客户端请求超时参数为 60 秒，不是整个刷新过程的硬截止时间。下载按块累积并限制清单 32,000 字节、目录 10,000,000 字节；压缩响应或未知总长度使用不确定进度，直到接收完成。之后在主 actor 之外完成哈希和目录校验，再执行原子安装。网络、完整性校验或安装失败继续保留旧内容及个人数据；排查时应区分线上版本、当前设备缓存版本与正在进行的更新，不将条目数本身当作安装成功的凭证。

## 回滚与恢复发布

发布版本保存在 R2 和本机 releases 下。使用下面的回滚命令，不直接上传旧 manifest；不要为恢复一次抓取而清空收藏或整个内容目录。

1. 从本机 `releases/<version>/manifest.json` 选择目标，执行 `npm run rollback -- <version>`。默认仅演练：读取线上当前与目标目录、核对校验和与条目数，合并目标／当前／本地全部下架 ID，生成独立的 `rollback-*` 版本；不切换线上、不改变下架记录或发布状态。
2. 确认 `rollback-status.json` 的目标和数量后，运行 `npm run rollback -- <version> --publish`。检查旧版本媒体可读取，上传并复核新目录，最后激活清单；上传失败记录到 `rollback-status.json` 和 `operations/rollback-*.json`。
3. 回滚激活前写入 `publication-hold.json`；已有暂停文件逐字节保留。下一次每日发布任务先续完自身待完成回滚，再在采集前停止，状态中带 `publicationHold`。不手动删除此文件；需要看新候选时单独运行不带`--publish`的daily。
4. 修复采集或编辑问题后，执行 `npm run daily` 查看候选，再运行 `npm run daily -- --publish --resume-publishing`。只有线上激活校验通过后才清除 hold。最后运行 `npm run check:deployment`。

采集、回滚、下架共用同一进程锁，避免本机发布交错。恢复发布会把线上有效下架记录合并到本地，因此恢复较旧备份不会让已下架条目重新出现。暂停发布期间的紧急下架：先 `npm run remove -- <id> <reason>`，再以当前线上版本作为回滚目标执行第 1、2 步。客户端下次更新会应用下架记录；保存在用户剪贴板或已经导出的内容无法远程撤回。

回滚要求本机目标清单仍在且对应远程目录可验证。丢失本地清单、媒体失效或当前版本无法校验时会停止，不猜测版本、不删除远程媒体。当前命令用于已建立的生产内容库；首次初始化仍通过经过检查的发布流程执行。

### v2分语言通道

双通道已部署并完成首次初始化，实际证据见下方0.3.2运行记录。新环境先部署只读Worker路由，再启用外部`~/.config/prompix/publication.env`中的`PROMPIX_LANGUAGE_PACKS_ENABLED=true`，升级定时运行器。首次只有真实404允许从已验证v1建立基线；超时、503、重定向或损坏清单不能当作“尚未初始化”。一旦本地状态或线上v2已存在，删除开关不能退回v1发布。原生0.3.2已接入v2网络和缓存，旧客户端继续使用v1。

`publication-state.json`保留初始化、v1冻结状态及待完成发布的已观察指针和目标身份。所有新不可变原文／语言文件先上传并回读，全量重组验证后才先激活v2、再激活v1。两次激活不是原子事务：失败后保留pending，下一次每日发布在任何抓取、媒体及付费准备之前续完同一目标，并结束当次运行。`status.json.channels`分开报告版本和`v1Frozen`；`recoveredPublication`表示只完成恢复。不要手动删除pending或把v1当成完整v2基线。

期间新增下架记录会先合并到待完成目标，生成新不可变版本，保留全部已备妥译文；不会重新调用模型。另一个进程改变远端指针时停止覆盖。显式回滚可以直接替代未完成的普通发布，不先激活待撤回目标；合并v1、v2、目标、本地及待完成目标的全部下架记录。回滚首次和恢复激活前均检查媒体可用，任何现有hold保持不变。恢复普通发布只清除最初明确选择的同一个hold，后来出现的暂停不能被顺带清除。

v1全语言目录超10 MB后只保留最后兼容快照并继续显式下架，后续小目录不自动解冻；v2仍提供完整内容。若全部兼容条目都被下架，旧v1不支持空目录，发布会在激活前失败，须单独处理旧协议空库兼容，不能补造条目。v2目标在本机使用`releases/<version>/v2/manifest.json`及原文／全部语言文件，manifest和index不是公开路径；缺失或损坏时不能回退同版v1。部署后运行`npm run check:deployment -- --require-v2`验证两通道和所有语言文件。

## 编辑发布

候选保存在 `candidates/`，编辑记录保存在仓库外的 `editorial.json`。用 `npm run review -- <candidate-id> /absolute/path/editorial-metadata.json` 写入标题、用途、示例、标签、封面和可选排序；字段说明见 [采集说明](../ingest/README.md)。原始正文与作者保持不变。编辑记录绑定正文指纹，来源正文变化后需要重新确认。

轻量增量审核可以在升级运行器后通过 `~/.config/prompix/editorial.env` 中的 `PROMPIX_EDITORIAL_PROVIDER=codex` 启用；固定使用 `gpt-5.6-luna`，默认每个 UTC 日最多四次请求，每次最多三条完整候选、16,000 字符输入。`PROMPIX_EDITORIAL_MAX_REQUESTS` 可配置为0–20的整数，0禁用新请求；正常一次发布运行会连续处理剩余名额内的批次，无须重复触发定时任务。每次调用前写入持久账本，失败、响应不明确或中断后未完成的预约阻止该阶段当天余下请求；已完成批次的审批继续保留。模型只整理标题、用途、使用建议、标签和封面文案，不改正文、来源、创作者、许可或媒体地址；拒绝和暂缓决定按正文指纹缓存。新批准内容继续走既有翻译、媒体与发布校验。普通 staging 不调用审核模型。详细开关、文件位置和状态字段见[采集说明](../ingest/README.md)。
