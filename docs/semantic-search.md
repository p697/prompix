# 图片语义搜索调研（2026-11-07）

目标：图里有红色袜子，搜「红色袜子」就能找到这条 Prompt，并且直接显示这张图；整体效果要超过 iOS 应用「寻隐」。本文只是调研，没有改产品代码和流水线。

## 结论

1. **在服务器上做，不在手机上做。** 搜索的是所有用户共享的同一份目录，图片向量和描述在服务器上算一次就行，App 体积不变，换模型也不用发版。寻隐要在手机本地算，是因为它搜的是用户自己的私人相册，前提和我们不同。
2. **第一阶段：每张图生成一段中英双语描述，配合向量混合检索。** 每张图用 Haiku 5.5 写一段中英文描述加关键词，再用 bge-m3 转成向量，和现有关键词搜索合并排序。在 300 张线上图片、64 个中文查询的测试里，前 5 条召回率从现在的 **0.32 提高到 0.79**，第一条就命中的比例从 0.31 提高到 0.84，全部只用现有的基础设施：Anthropic API、Workers AI 和现在这个 Supabase。整个图库补一遍描述约 3 美元，之后每天约 0.1–0.2 美元。
3. **第二阶段：加图片向量，主要提升颜色和服饰类查询。** 再加上 Chinese-CLIP B/16 的图片向量，召回率到 0.84，颜色服饰类从 0.58 提高到 0.73。代价是查询时要有一个能跑文本编码器的小服务，Workers AI 上没有这类模型，所以等第一阶段上线、看过真实查询之后再决定做不做。
4. **为什么能比寻隐好：**
   - 中文查询原生支持；
   - 能直接显示命中的那张图（27% 的条目有多张图）；
   - 和标题、作者的关键词搜索混合排序；
   - 有相似度下限，不会硬凑出不相关的结果；
   - 新内容自动入库，不用手动建索引。
5. **寻隐用的模型不能直接拿来用。** MobileCLIP 直接搜中文时召回率只有 0.08。寻隐中文版靠的是一个没有开源的中文文本编码器，而且 MobileCLIP 的权重现在只许研究用途。

## 现状

- `services/feed/queries.ts` 的搜索是 `search_text` 上的 `pg_trgm` 子串匹配：
  - 查询按空格拆开，所有片段都要命中才算匹配；
  - 排序依次是完整标题、标题、作者、元数据。
- 中文没有空格，「拿着相机的女孩」只能整句去匹配原文，所以查不到画面里有、但文字里没写的东西。
- Prompt 原文很少写颜色和小物件。测试里颜色服饰类查询的召回率只有 0.11。

## 寻隐（Queryable）为什么小、为什么快

寻隐的源码是 MIT 许可，开源在 [mazzzystar/Queryable](https://github.com/mazzzystar/Queryable)。我读的是 `19825fa` 版本。

**模型**
- 2024 年起改用 Apple MobileCLIP-S2：图片编码器 3570 万参数，文本编码器 6340 万参数，向量 512 维。
- 打包成 Core ML、半精度，模型文件一共不到 200 MB。
- 这就是整个 App 只有 160–210 MB 的原因：模型本身就小。
- 更早用的是 CLIP ViT-B/32。

**中文**
- 中文版是另一个 App。作者训练了一个中文文本编码器，对齐到英文模型的向量空间，花了约 70 美元和 3 天，但这个编码器没有开源。
- 作者在 issue #10 里说，不用多语言模型是因为 App 会超过 1 GB。

**索引和检索**
- 图片直接拉伸到 256×256，不裁剪，每批 32 张。
- 向量存在自定义的二进制文件里。
- 搜索时在 GPU 上逐条算相似度，固定返回 120 条，没有关键词混合，也没有相似度下限。
- 新照片要手动重建索引。

**速度**
- iPhone 12 mini 上约每分钟 2,000 张。
- 1 万张以内的相册，搜索不到 1 秒；30 万张约 45 秒。
- 有人反馈相册到 1.5–2.4 万张时会崩溃。

**fork 和同类项目**
- Norod/Queryable-mobileclip 只做了小改动。
- 安卓的 PicQuery 用 MobileCLIP2，在手机上先把中文翻译成英文再搜。
- MaterialSearch 用 Chinese-CLIP。
- Immich 用 nllb-clip / SigLIP 系列。Immich 社区的对比显示，FG-CLIP2-base 在中文 XM3600 上明显更好（90.07 对 82.10）。

**更新的开源模型**
- FG-CLIP2（Apache-2.0）：中文检索指标超过 Chinese-CLIP。我在本机加载时报错，没有测成。
- Qwen3-VL-Embedding-2B（Apache-2.0）：效果强，但模型约 4 GB，本机跑会把内存吃满，见「实验」。
- jina-clip-v2、jina v4/v5 和 MetaCLIP2 是非商用许可，排除。

## 实验

### 做法

**图片和查询**
- 从 `/v3/feed?kind=image` 取 300 条线上图片，每条只用封面图。
- 写了 64 个中文查询，每个配一个人工英文翻译，分成三组：
  - 颜色服饰 16 个，例如「红色外套」「条纹长袜」；
  - 小物件细节 15 个，例如「小笼包」「香蕉皮」「用吸管喝饮料」；
  - 主体场景风格 33 个，例如「东方明珠」「黑白照片」「拼贴风海报」。
- 这批样本里没有单纯「红色袜子」的图。最接近的是一张红黑条纹长袜，由「条纹长袜」这一题和颜色服饰组代表。

**标注**
- 前 80 张由我逐张标注，共 93 个正确结果。
- 后 220 张采用汇总判定：取几种方法排在前面的候选图，交给 Claude Opus 5.5 逐张判断（标准从严，例如拿手机不算拿相机），我再抽查。新增 115 个正确结果，花了 1.41 美元。

**指标**
- R@5：前 5 条里找回了多少正确结果。正确结果超过 5 个时按 5 个算满分。
- 首位命中：第一条就是正确结果的比例。
- MRR：第一个正确结果排名的倒数，再取平均。

**描述**
- 「描述」是模型在看不到测试查询的情况下，为每张图写的中英文描述加 15–30 个关键词。

**混合**
- 用 RRF 合并：每路取前 50 条，k=60。

| **第二阶段**：Haiku 描述向量 + Chinese-CLIP B/16 + 线上关键词 | **0.84** | **0.88** | **0.91** | 0.73 | 0.86 | 0.89 |
| 全部合并：再加 SigLIP2 B/16（查询人工译成英文） | 0.87 | 0.91 | 0.93 | 0.77 | 0.85 | 0.92 |

只有 80 张时所有方法都更容易，例如 Chinese-CLIP B/16 是 0.91，现状是 0.34。当时还测了几项：

- Prompt 原文 + bge-m3：0.66，并且混进去反而拉低结果。原因是 Prompt 写的是「想要什么」，不是「画面里有什么」。
- Sonnet 描述 + bge-m3：0.86，和 Haiku 的 0.85 差不多。
- Qwen3-Embedding-0.6B 比 bge-m3 略好（0.90 对 0.85），但不在 Workers AI 上。

**怎么读这张表**
- **描述**能补上 Prompt 里没写的画面内容，小物件和场景提升最大。Sonnet 比 Haiku 贵约 20 倍，效果没有明显更好，选 Haiku。
- **图片向量**对颜色和服饰最有用（0.58 → 0.73）：描述会漏掉配角身上的颜色，而图片向量直接看像素。
- **「查询人工译成英文」**用的是人工翻译，代表上限。真实上线要靠机器翻译，效果会打折扣。
- **以下几项没有测：**Haiku 描述与 bge-m3 组合时的混合权重和相似度下限、多张图的条目、视频，以及日语、韩语以外的其他语言查询。

**局限**
- 查询是我看过前 80 张后写的。
- 汇总判定只看了几种方法排在前面的候选，排在后面的正确结果可能被漏标，所以各方法的召回率都略偏高，但不影响相互比较。
- 64 个查询仍然偏少，上线前应该用真实搜索词再验证一轮。

**本机的教训：**同时下载和运行好几个大模型会把 16 GB 内存吃满，Qwen3-VL-2B 那次直接让电脑卡住。正式方案只调用 Haiku API 和 Workers AI，不会在这台 Mac 上跑模型。

## 推荐方案

```
流水线（每日）                               feed Worker（/v3/feed?q=）
图片审核通过 → describe 环节（Haiku）         查询 → bge-m3（Workers AI，结果缓存）
  按媒体 sha256 存描述，没变过的图不重算         ├ 向量最近邻：media_search.text_vec
  → bge-m3 文档向量                            ├ 关键词：search_text（已包含图片描述）
发布 → prompix.media_search（pgvector）        └ RRF 合并 + 相似度下限 → 卡片 + 命中的图片序号
     revisions.search_text 追加描述
```

### 流水线：新增 `describe` 环节

**调用方式**
- 走模型插件层：`npm run pipeline -- route describe anthropic-api`，模型用 `claude-haiku-5-5`，备用路由按现有规则配置。
- 输入是单张图，长边缩到 1024 px。
- 输出 `{zh, en, tags_zh, tags_en}`，用 zod 校验。提示词沿用实验里的「盲写」版本，存在外置盘的 `scripts/caption.py`。

**存储和增量**
- 结果按媒体 sha256 存在内容目录（例如 `search/descriptions/<sha256>.json`），并记下模型和提示词版本。
- 图片是按内容寻址的（`/media/<sha256>.jpg`），没变过的图永远不重算。换模型或改提示词时，只需按版本号重跑。

**失败和花费**
- 失败或拒答只会让这张图没有描述，不阻塞发布；这条内容仍能被关键词搜到。
- 花费计入 Anthropic 每日 2 美元的上限。日常 0.1–0.2 美元够用；补全库约 3.3 美元，要分两天跑，或者临时提高上限。

**补存量**
- 用一次性命令，可以参照 `scripts/enrich-catalog.ts`。
- 这些改动由数据管线会话负责，本调研没有动流水线。

### 数据库

**表结构**
- 启用 `vector` 扩展。
- 新表 `prompix.media_search`：`sha256` 为主键，存 `description jsonb`、`text_vec vector(1024)`、`image_vec vector(512)`（可为空，第二阶段才填）、模型版本和时间。
- 条目与图片的对应关系来自 `media.imageURLs`（第一张就是封面）。发布时写入 `(revision_id, media_index, sha256)`，用来查回命中的是第几张图。

**接入关键词搜索**
- `prompix.search_fields` 把这条内容所有图片的描述也拼进 `search_text`，现有关键词搜索就能直接查到画面内容。实验里这一路单独有 0.44，合并后贡献明显。

**索引**
- 5,500 条做精确扫描，开销在毫秒级（估算）。超过约 5 万条再加 HNSW 索引。

### feed 服务

**查询向量**
- `wrangler.jsonc` 加 Workers AI 绑定，查询时调用 `@cf/baai/bge-m3`，和文档向量是同一个模型。
- 查询不是中文时，先翻译成中文再算向量，见下面的「多语言」。
- 查询向量和译文都按「规范化后的查询词 + 模型版本」缓存。

**召回和合并**
- 有 `q` 时取两路候选：
  - 向量最近邻前 50 条，一个条目取它各张图里分数最高的；
  - 现有关键词排序前 50 条。
- 两路用 RRF 合并。
- 只有向量命中、关键词没命中的条目，必须超过相似度下限才保留。下限用评测集来定，避免像寻隐那样永远返回一堆勉强的结果。

**可见性和分页**
- 所有候选都经过现有的 `visible_entries`，下架和隐藏规则不变。
- 合并后的结果是固定的前 N 条（例如 120），游标记住它在这个列表里的偏移量。没有 `q` 的浏览和分页完全不变。

**返回字段**
- 卡片增加可选的 `match: { mediaIndex }`，旧版 App 会忽略这个字段。

### iOS

- `SearchView` 和 `FeedQuery` 不用改，服务器搜索本来就走 `/v3/feed?q=`。
- 卡片拿到 `match.mediaIndex` 后，在搜索结果里显示命中的那张图，点开详情时也停在这张图上。
- 不加解释性的小字或标签，保持界面克制。是否提示「为什么匹配」见下方的决策 2。

### 多语言

**不用按语言重做向量**
- 每张图只存一份描述向量。新增一种语言时，库里什么都不用重算。

**但直接用其他语言搜会变差，查询要先译成中文**
- 把 64 个查询译成日语和韩语，在同一批 300 张图上测（`exp/data/results300_multilingual.md`）：

| 查询方式 | R@5 | 首位命中 |
|---|---|---|
| 中文，描述向量 | 0.72 | 0.80 |
| 英文，描述向量 | 0.65 | 0.67 |
| 日语直接搜，描述向量 | 0.49 | 0.45 |
| 韩语直接搜，描述向量 | 0.44 | 0.38 |
| 日语先译成中文，描述向量 | 0.72 | 0.78 |
| 韩语先译成中文，描述向量 | 0.71 | 0.78 |
| 中文，第一阶段混合 | 0.78 | 0.86 |
| 日语先译成中文，第一阶段混合 | 0.76 | 0.80 |
| 韩语先译成中文，第一阶段混合 | 0.78 | 0.80 |

- **测试条件：**日语、韩语查询由 Sonnet 写成母语用户会输入的说法，再用 Haiku 译回中文，模拟查询时的翻译。关键词这一路用的是日语、韩语原文在线上接口的搜索结果，因为标题和 Prompt 已有九种语言的译文。
- **原因：**描述是中英文写的，跨语言匹配比同语言匹配弱。英文查询也比中文低一截。
- **做法：**feed 收到非中文查询时，先译成中文。语言检测和翻译结果都缓存，同一个查询词只翻译一次。
  - 用 Haiku 翻译，每次约 100 个 token，每百万次查询约 60 美元，缓存命中后不再花钱；会增加一次调用的延迟，还没实测。
  - Workers AI 的 `@cf/meta/m2m100-1.2b` 更便宜，但翻译短查询的质量还没有测。
- **其他语言：**西班牙语等其他语言没测，按同一个原理处理。

### 第二阶段：图片向量

**怎么做**
- 用 Chinese-CLIP B/16 给每张图算 512 维向量，存进 `image_vec`。
- 约 1.9 亿参数，半精度不到 0.4 GB；CPU 上每秒十几张，在流水线里每天几十秒就算完。
- 也可以放到云端容器里算，不占本机内存。
- Chinese-CLIP 的代码是 MIT 许可，上线前还要核对权重的许可。

**难点在查询这一端**
- 中文文本编码器（约 1 亿参数）需要一个常驻的小服务，比如 Cloudflare Containers。Workers 本身的内存放不下。
- 有了这个小服务，可以把 SigLIP2 加上查询翻译一起评估：表里的人工翻译上限是 0.87。

**先试更便宜的办法**
- 改进描述提示词，要求逐个人物写出颜色、服饰和配饰，看颜色组能补回多少。

### 第三阶段

- **视频：**取首、中、尾三帧写描述，成本约是图片的三倍。
- **重排：**对前 50 条用 Qwen3-VL-Reranker 这类模型重排。它太大，要放在云端，等真实查询日志出来再看值不值得。

## 需要 Lucy 决定

1. **搜索结果的封面要不要换成命中的那张图？** 推荐换，这是超过寻隐的关键体验。
2. **要不要提示「为什么匹配」**，例如在卡片上写「画面中：香蕉皮」？推荐第一版不加，保持界面克制。
