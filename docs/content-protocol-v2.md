# 按语言分发协议

状态：协议与纯编解码已实现并完成本地验证，尚未启用线上端点或原生客户端下载。旧版仍使用 `/v1/latest.json`；本文件不是已上线能力声明。

## 要解决的问题

当前346条内容的紧凑九语目录为7,345,871字节，接近v1解码后的10 MB限制。每次内容更新都下载所有语言，既限制扩量，也增加首次更新等待。v2保留完整原文和所有来源、作者、Skill及媒体字段，把译文分为独立的不可变语言文件。用户需要哪一种语言，客户端下载哪一种；缺少对应译文时显示原文，不隐式下载或回退英语。

发布器内部仍使用完整多语言目录。拆分只发生在发布边界；继续审核、翻译、保留上次快照和回滚时，必须重新组装所有已发布语言，不能把某台设备只下载的一个语言当成完整发布状态。

## 数据约定

新清单使用 `schemaVersion: 2`、发布版本、时间、条目数，以及原文文件和各语言文件的描述符。描述符包含固定HTTPS地址、SHA-256、解码字节数及条目数。原文文件位于 `releases/<version>/v2/base.json`，语言文件位于 `releases/<version>/v2/locales/<locale>.json`。只接受现有九种语言。

原文文件保留原始字段与下架ID。已有本地化元数据保留来源语言和完整源文指纹，将译文字典替换为明确的可用语言列表；没有本地化元数据的原条目不补造来源语言。源文指纹覆盖标题、摘要、正文、示例、预览说明和封面文案，不能只比较Prompt正文。

每个语言文件绑定发布版本、时间、语言和原文文件哈希，包含条目ID、源文指纹及完整译文。该语言文件必须完整覆盖原文文件中宣告可用的条目；不接受重复、未知、已下架、未声明或指纹不一致的条目。语言缺项与“尚未下载”是不同状态，后者不能被当作撤回译文。

清单最多32,000字节；原文、每个语言文件，以及原文加任一所需语言文件的解码总量均不得超过10,000,000字节。此步保留1,000条上限，不靠提高单个路径的容量或静默截断来扩量。每个文件的哈希、实际字节、条目数和固定地址都要验证，HTTP压缩不能绕过上限。

## 后续接入顺序

1. 完成纯拆分、验证、原文加单语言、全部语言重组及合成错误测试；用仓库外真实目录验证无内容丢失和传输体积。
2. 增加严格的Worker只读路径和两通道发布／回滚。全部不可变文件上传并回读校验后才激活清单；重试复用原字节和发布时间。v1和v2的两个清单不是一个原子事务，必须分开报告并能从中断恢复。
3. 原生客户端在现有文件事务中加入活动v2清单。已验证文件先暂存，再与收藏、创作者和下架清理一并提交；失败保留旧目录。语言切换同样检查当前版本下是否已有正确哈希的语言文件，不能因为版本号相同就跳过。
4. 为每次下载保留任务代次，语言切换取消旧任务；校验和安装前再次确认代次、来源身份及下架状态。已打开详情页要跟随对应内容更新，编辑器打开后则保持语言和草稿上下文稳定。
5. 收藏仅在完整源文指纹一致时合并已验证译文，保留已下载语言并尊重明确撤回。原文或指纹改变时继续保留原收藏快照，不能把新译文混入旧正文。草稿继续使用 `id` 和 `id::locale`，下载、语言切换和缓存清理不改写草稿。

新协议完全接通前不冻结v1。其后若完整v1超过容量，保留最后一个可用版本，并继续显式下架的兼容更新，不能把v2文件放到v1地址或隐瞒丢弃内容。v2成为发布保留依据后，后续目录不得从停留在旧版的v1重建。

## 验收边界

纯编解码通过只说明传输协议可用，不代表每日发布、网络端点、缓存迁移或原生语言切换已完成。最终验证必须覆盖同版本切换语言、离线已有语言、下载失败、快速来回切换、收藏旧译文、两种语言草稿、下架、事务写入故障和重启恢复。既有Granola视觉及四类发现结构保持，由原生现有交互承接状态。
